优势 vs 短板

▲ 核心优势
  • 工程规范度超出项目年龄：2 周个人项目却具备完整 CI/CD、规范 CHANGELOG、踩坑文档体系。
  • 架构干净可演进：数据层（HolidayStore / Support）与视图层解耦，重构成本低。
  • 隐私即卖点：完全离线、无埋点，对注重隐私的目标用户极具吸引力。
  • 定位清晰克制：明确「不做 EventKit、不做商业化」，避免范围蔓延。
▼ 关键短板
  • 未公证：劝退最严重的单点，所有新用户第一步即受阻。
  • 仅 arm64：直接放弃 Intel Mac 存量用户。
  • 数据会静默过期：2027+ 调休缺失且无应用内提示。
  • 首屏空白：README 无截图，开源转化率受损。
  • 测试盲区：UI / 更新流程无回归保护（更新功能曾连发多个测试版本调试）。

优化方案 · 可直接落地

01

接入 Apple 公证（Notarization）

P0 · 最高
问题：release.yml 仅做 ad-hoc codesign --sign -，DEVELOPMENT_TEAM 为空。结果是每个新用户首次打开都撞 Gatekeeper「已损坏」，需手动 xattr -cr——这是整条转化漏斗最前端、流失最严重的一环。
方案：升级为 Developer ID 签名 + Hardened Runtime + notarytool 公证 + stapler 装订。项目已设 ENABLE_HARDENED_RUNTIME: YES，前置条件已具备，只差证书与 CI 步骤。落地后可直接删掉 README 那段 Gatekeeper 说明。
关键 CI 步骤（替换现有 “Ad-hoc sign” 步骤） 
# GitHub Secrets: DEVELOPER_ID_P12(base64)·P12_PASSWORD·AC_KEY_P8(base64)·AC_KEY_ID·AC_ISSUER
- name: Import Developer ID cert
  run: |
    security create-keychain -p "" build.keychain
    security default-keychain -s build.keychain
    security unlock-keychain -p "" build.keychain
    echo "$DEVELOPER_ID_P12" | base64 --decode > c.p12
    security import c.p12 -k build.keychain -P "$P12_PASSWORD" -T /usr/bin/codesign
    security set-key-partition-list -S apple-tool:,apple: -s -k "" build.keychain

- name: Sign & notarize
  run: |
    codesign --force --options runtime --timestamp --deep \
      --sign "Developer ID Application: 你的名字 (TEAMID)" "$APP_PATH"
    # …make-release-dmg.sh 生成 $DMG…
    echo "$AC_KEY_P8" | base64 --decode > ac.p8
    xcrun notarytool submit "$DMG" --key ac.p8 \
      --key-id "$AC_KEY_ID" --issuer "$AC_ISSUER" --wait
    xcrun stapler staple "$DMG"
影响极高 成本$99/年 + 半天 CI 调试 收益首次打开零摩擦 · 信任度↑ 触点.github/workflows/release.yml
02

产出 Universal Binary 覆盖 Intel

P1 · 高性价比
疑似根因：project.yml 写的是 ONLY_ACTIVE_ARCH_Release: "NO"——这不是有效的 build setting key（正确应为 configs.Release.ONLY_ACTIVE_ARCH），很可能被静默忽略。叠加 CI build 未显式指定 ARCHS，于是 Apple Silicon 的 macos-15 runner 只产出 arm64，把 Intel 用户拦在门外。
方案：修正配置写法 + 在 Release build 显式 ARCHS="arm64 x86_64"，一份 DMG 通吃全部 Mac。几乎零成本（改两处配置），是性价比最高的 quick win。
两处改动 + 一行校验 
# ① project.yml —— 用合法的 config 条件写法
settings:
  base:
    ARCHS: "arm64 x86_64"
  configs:
    Release:
      ONLY_ACTIVE_ARCH: NO

# ② release.yml Build 步骤显式声明（双保险）
xcodebuild build … ARCHS="arm64 x86_64" ONLY_ACTIVE_ARCH=NO

# ③ 打包前校验，期望输出: arm64 x86_64
lipo -info "$APP_PATH/Contents/MacOS/Tic"
影响高（覆盖 Intel 存量） 成本极低（改 2 处配置） 前提LunarSwift 走 SPM 源码编译，原生支持 x86_64 触点project.yml · release.yml
03

消除节假日数据「静默失效」

P1 · 防雷
问题：内置数据止于 2026，离线优先后无联网刷新。一旦 2027 维护者遗忘发版，用户看到的是「整年无节假日标注」且毫无提示，会误判为应用出错。需在不违背离线优先的前提下兜住。
方案（两个互补，皆轻量）：
A · 应用内兜底提示——浏览年份超出内置范围时，月历/设置给一条非阻断提示，避免误解。
B · CI 数据哨兵——定时探测上游 holiday-cn 是否已发布次年数据，若已发布而仓库未内置则自动开 Issue 提醒。保留「维护者发版」模式，仅消除「忘记」风险。
A：HolidayStore 暴露覆盖范围（Swift） 
// loadBundled() 内 apply(days:) 成功后追加：coveredYears.insert(year)
private(set) var coveredYears: Set<Int> = []

/// 某年是否缺少官方调休数据（供 UI 做非阻断提示）。
func isYearUncovered(_ year: Int) -> Bool {
    !coveredYears.isEmpty && !coveredYears.contains(year)
}
// 月历头部：if HolidayStore.shared.isYearUncovered(viewedYear) { 显示「2027 放假安排待更新」}
B：定时哨兵 workflow（每周探测次年数据） 
on:
  schedule:
    - cron: "0 1 * * 1"   # 每周一
jobs:
  probe:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: |
          NEXT=$(( $(date +%Y) + 1 ))
          [ -f "Tic/Resources/holidays/$NEXT.json" ] && exit 0
          URL="https://cdn.jsdelivr.net/gh/NateScarlet/holiday-cn@master/$NEXT.json"
          if curl -fsSL "$URL" -o /tmp/n.json; then
            gh issue create --title "内置 $NEXT 年调休数据" \
              --body "上游已发布 $NEXT 年安排，请落入 Resources 并发版。"
          fi
        env: { GH_TOKEN: "${{ secrets.GITHUB_TOKEN }}" }
影响中（防长期口碑塌方） 成本低（~半天） 原则不破坏离线优先 触点HolidayStore.swift · 新增 workflow

05

延伸测试到当前盲区

P2 · 稳健
问题：19 个测试只覆盖日历逻辑层。菜单栏文案拼装、HolidayStore 越界年份、UpdateService 边界（预发布 tag / 版本相等）等纯逻辑盲区无回归保护——而更新功能此前正因缺测试连发多个调试版本。
方案：优先补「纯逻辑可测」盲区（MenuBarDisplayComposer 拼装、HolidayStore.isYearUncovered、UpdateService 边界），而非急于上 XCUITest——CI 已就绪，收益快且稳。
影响中（重构信心） 成本低（增量） 触点TicTests/
06

补齐全局快捷键 K1

P2 · 体验闭环
问题：plan.md 与 README「已知限制」都点名、却仍未实现的唯一「功能型」缺口——唤起日历必须先点菜单栏图标。设置页快捷键分区已有占位，体验差一口气。
方案：用全局热键注册（NSEvent 全局监听 / Carbon RegisterEventHotKey 或 MASShortcut 类库），接到现有弹窗锚定逻辑（MenuBarPopoverWindowAnchor），并在快捷键设置页提供录制控件。
影响中（补齐承诺） 成本中（1–2 天） 触点ShortcutsSettingsVC · 弹窗锚定
